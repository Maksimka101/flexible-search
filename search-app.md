# Поиск с плагинами — заметки

Продолжение `self-modifying-apps.md` (полигон 2: лаунчер + поиск).

# Часть 1. Решения

## Продукт
- Android-приложение поиска, весь UI на Compose.
- Основа — layout Pixel Search (скриншот
  `DCIM/Screenshots/Screenshot_20261018_113340_Pixel Search.jpg`).
- Каждая мельчайшая часть изменяема и дополняема, и UI, и логика.
  Всё построено на базовых компонентах.
- Плагины загружаются через DexClassLoader.

## Архитектура
- Тонкий core. Изменения на уровне данных (JSON-оверлеи, порядок и
  отключение плагинов) делаются плагинами, а не в core.
- Никакого UI-фреймворка поверх Compose: ни своего дерева layout,
  ни своих токенов, ни своего UI-кита.
- Вместо этого система компонентов на Compose. Плагин может подменить
  любой компонент в любом месте, частично или целиком.
- UI по умолчанию лежит в core, стиль компонентов настраивают плагины.
- Нужен небольшой DSL, чтобы плагин мог просто показать результат,
  не трогая Compose.
- Названия читаемые: `Middleware`, а не `Mw`.

## Направление для PoC (пример одобрен)
- `Component(name, defaultStyle) { props, style -> ... }` в core.
  Вызывается как обычный composable: `SearchBar(SearchBarProps(...))`.
- Три возможности плагина:
  - `scope.style(SearchBar) { it.copy(...) }` — поменять вид;
  - `scope.override(SearchBar) { props, style, original -> ... }` —
    обернуть, дополнить или заменить (не вызывать `original`);
  - `scope.results { query -> card(...) }` — результат без Compose,
    рисуется компонентами core (`ResultCard` и т.п.).
- Первые плагины: стиль строки («таблетка»), погода над строкой,
  калькулятор. В PoC они встроенные, без DexClassLoader.

## Решения после PoC `components` (2026-10-20)
Проект `~/develop/flexible-search`, PoC в `poc/<имя>`.
- Layout-компоненты принимают детей слотами-лямбдами (`SearchLayout`
  получает `searchBar`, `loading`, `results`), а не вызывают дочерние
  компоненты сами. Props детей всё равно лежат рядом, но так компоненты
  чище и независимее, core проще тестировать.
- Доп. данные для кастомного компонента плагин держит в своём
  состоянии (свой объект / `CompositionLocal`), core их не передаёт.
- Параметры по умолчанию — гибкость без обязательной настройки.
  Пример: `ResultsProps(items, targetIndex = 0)`. Цель Enter и
  подсветка — `items[targetIndex]`, по умолчанию первый результат.
- Провайдер результатов — `(query) -> Flow<List<ResultItem>>`.
  - Каждый `emit` — полный текущий список провайдера, не добавка
    (кэш, потом сеть — два `emit`).
  - `results { query -> card(...) }` — сахар для одного ответа;
    `resultsFlow { query -> flow { emit(buildResults { ... }) } }` —
    для нескольких.
  - Движок собирает провайдеры на `Dispatchers.Default`, плагину не
    нужно помнить про `flowOn`. Выход — `conflate()`.
  - Лимит времени на провайдер (~~5 с~~ 30 с, см. 2026-10-22), после —
    отмена. Упал или превысил лимит — остаётся его последний список,
    ошибка в лог.
  - `id` результата уникален в пределах плагина, движок ключует
    `плагин/id`.
- ~~Исторический порядок результатов~~ — заменён группами (ниже).
- Пока новый запрос не ответил, видны прежние результаты с
  `loading = true`, без мигания пустым списком.
- Индикатор загрузки (`LoadingIndicator`, компонент): показывается,
  только если загрузка идёт дольше `showDelayMs` (300 мс), и держится
  минимум `minVisibleMs` (500 мс). Тайминги — в стиле компонента.
  ~~`loading` = хотя бы один провайдер ещё не завершился~~ — только
  до первого ответа, см. 2026-10-22.
- Код: ktfmt (kotlinlang style), 76 колонок — ширина текста в nvim на
  разложенном экране.
- Ряд быстрых действий под результатами, виден всегда:
  `scope.quickAction(label, icon, isSelected) { ... }`. Порядок кнопок —
  порядок плагинов. Первые: «искать в…» (Google, Maps, Play — строка
  уходит в приложение) и кнопка калькулятора.
- Действие результата или кнопки получает `ActionScope`: `context`,
  `close()`, текущий запрос, `setQuery`.
- Тип клавиатуры и подсказка — параметры `SearchBarProps`
  (`keyboardType`, `placeholder`), по умолчанию текст и подсказка из стиля.
  Props компонентов — data class, чтобы override менял поле через `copy`.
- Режима поиска в core нет. Вместо него префикс-команды (триггеры):
  - `val calc = scope.trigger("Calculator", "calc", "=", placeholder = "2+2")`,
    результаты — `scope.results(calc) { query -> }`, глобальные —
    `scope.results { query -> }`.
  - Есть префикс — запрос получают только провайдеры этого триггера, и
    им приходит остаток без префикса, даже пустой. Без префикса —
    глобальные провайдеры, только на непустую строку.
  - Словесному префиксу нужен пробел (`calc 2+2`, а `calculator` — обычный
    поиск), символьному нет (`=2+2`). Регистр не важен. Одинаковые
    префиксы — побеждает первый плагин, в лог предупреждение.
  - Префикс показывается чипом (компонент `TriggerChip`, текст — `label`),
    в поле только остаток. Подсказку в пустом поле задаёт триггер.
  - Выход из префикса общий, в core: Backspace на пустом остатке, «Назад»,
    нажатие на чип. Набранный текст остаётся.
  - Остальное плагин делает сам: клавиатуру — через `override(SearchBar)`
    по `props.trigger`, кнопку — `setQuery("calc ")`.
  - Состояние строки — триггер + текст; `setQuery` и набор текста
    превращают префикс в начале строки в чип.

- Результаты — группы, группа = провайдер плагина, заголовок —
  `results(title = "Files")`. Порядок групп фиксированный = порядок
  плагинов, от запроса к запросу раскладка не меняется. Первая группа —
  у клавиатуры (список снизу вверх, `LazyColumn(reverseLayout)`);
  сейчас: приложения, калькулятор, веб, файлы.
- В группе до 3 строк. `results(fullList = trigger)` — заголовок
  «All ›» включает префикс группы, там она целиком. Полный список
  группы идёт сверху вниз.
- Примитивы DSL: `card` (крупный ответ), `app` (плитка в ряду), `item`
  (строка: превью/иконка, заголовок с подсветкой, подпись), `suggestion`
  (текст, `↖` подставляет его в строку, чип остаётся). Остальное — через
  `override`.
- Превью у `item` — ленивый загрузчик `thumbnail = { ... }`: грузится,
  пока строка на экране, кэш в core (LRU по ключу «плагин/id»).
- Fuzzy-поиск — примитив core `Fuzzy.match` / `Fuzzy.rank`, своя
  реализация в духе fzf v1 (готовой стандартной библиотеки нет:
  fuzzywuzzy — Левенштейн без позиций, commons-text `FuzzyScore` — без
  позиций). Подпоследовательность, бонусы за начало слова и подряд
  идущие символы, слова запроса в любом порядке, без учёта регистра,
  диакритики и `ё`; отдаёт позиции для подсветки.
- `Fuzzy` переименован в `NameMatcher`: поиск по названиям так, как их
  набирают, — нечётко, в другой раскладке и транслитом. Варианты
  запроса (`QueryVariants`) включены по умолчанию,
  `variants = QueryVariants.None` — только набранное. Core не переписывает
  запрос для всех: калькулятор, веб и префиксы получают ровно набранное,
  варианты включает тот, кто вызывает `NameMatcher`.
  - Варианты: другая раскладка (таблица ЙЦУКЕН ↔ QWERTY в core; без букв
    — нет варианта, `12+` остаётся `12+`), транслит (`android.icu`:
    кириллица → латиница по `Russian-Latin/BGN`, обратно —
    `Latin-Cyrillic`), транслит другой раскладки.
  - Вариант применяется к запросу, не к тексту: позиции подсветки
    остаются позициями в названии. Совпадение по варианту теряет 10 %
    очков.
  - `minSdk = 29` ради `android.icu.text.Transliterator`.
- Иконки у плагинов: `trigger(..., icon = ...)` — в чипе перед
  названием, `results(title, icon = ...)` — в заголовке группы. Тип —
  `ActionIcon` (значок приложения или вектор); `materialIcon(name, path)`
  в core собирает вектор из `pathData` Material Symbols без
  material-icons.
- Текст в строке сменили снаружи (`↖`, префикс стал чипом) — курсор в
  конец; при обычном наборе курсор не трогаем.
- Окно поиска ведёт себя как обычное приложение: есть в
  многозадачности, строка сохраняется; `close()` уводит в фон
  (`moveTaskToBack`), а не закрывает. К поведению «окна поверх всего»
  (как Pixel Search) вернуться, когда поиск станет точкой входа.
- Моки для UI: веб-подсказки (задержка 150–400 мс), файлы (размер ·
  дата · папка, превью-заглушки с задержкой).
- Виджеты пустой строки (нет текста и префикса): `widget { card(...) }` —
  один ответ, `widgetFlow { flow }` — живой. Виджет = группа
  результатов на том же DSL, видны все строки; пустой список — виджета
  нет. Порядок = порядок регистрации, первый у клавиатуры. Поток
  собирается, пока окно на экране (`collectAsStateWithLifecycle`), и
  перезапускается при открытии — это и есть обновление. Без лимита
  времени, упавший виджет скрывается.
  - Не делаем: смахивание, кэш в core (кэширует сам плагин), состояние
    «нужно разрешение» в core (плагин рисует сам), pager — пока только
    список (`WidgetArea`, меняется через `override`).
  - Своя отрисовка — `custom(id) { @Composable ActionScope.() }`, тип
    `ResultItem.Custom`; работает и в обычных результатах. Enter на нём
    ничего не делает. `ActionScope` приходит через `LocalActionScope`.
  - Демо: `TogglesPlugin` (фонарик с живым состоянием, таймер,
    будильник, камера), `WeatherPlugin` (мок).
- Пустая строка без префикса — тоже запрос: провайдер с
  `results(onEmpty = true)` получает и её (недавние, предложенные).
  Виджеты над такими результатами, результаты у клавиатуры; порядок
  групп тот же, по регистрации. Enter — первый результат.
  - Что релевантно на пустой строке, решает сам плагин. Core не
    смешивает и не ранжирует результаты разных плагинов.
  - `AppsPlugin`: недавно запущенные отсюда, новые первыми, до 5, в
    `prefs`. Свои нажатия плагин видит сам (это его `action`), для
    этого история в core не нужна.
  - Ряд плиток общий: `app(...)` любого плагина попадает в один ряд
    (`withSharedAppRow()` в `Results`), на место первой группы с
    плитками. Порядок — по регистрации плагинов, мест 5; кто раньше,
    тот и занял. Ставить плитки может кто угодно и всегда: при наборе
    — `results { app(...) }`, на пустой строке — `results(onEmpty =
    true) { app(...) }`. Недавние приложения могут занять все места —
    так и оставляем.
- Общие сервисы для плагинов — в core, через `PluginScope`:
  - `prefs` — свой `SharedPreferences` (`plugin_<id>`). Данные плагинов
    не смешиваются, хосту видно, чьи они (удаление, экспорт). Пока только
    ключ-значение; базу плагин держит сам.
  - `http` — один `OkHttpClient` на всех: общий пул соединений и кэш
    (`cacheDir/http`, 10 МБ), создаётся при первом запросе. В корутинах —
    `executeAsync()` из okhttp-coroutines.
  - `json` — один kotlinx.serialization `Json`
    (`ignoreUnknownKeys`, `coerceInputValues`).
  - Обёрток над библиотеками нет: в `PluginScope` только то, где нужен
    хост (id плагина, жизненный цикл, UI). Библиотеки — общие
    зависимости хоста, их версии — часть контракта с плагинами.

## Решения 2026-10-22
- Fuzzy: лимит разрыва между совпавшими символами (`te` не должен
  находить `boarding pass TIV-BEG.pdf`).
- Frecency живёт в плагине (у `AppsPlugin` история уже в `prefs`), не
  в core.
- Опечатки: второй проход через `LevenshteinDistance` (commons-text),
  если fuzzy ничего не нашёл. Будет много нерелевантного — откатить.
- Общий индикатор загрузки — только до первого ответа (`emit`) каждого
  провайдера. Дальше обновления идут без него: быстрые плагины
  (приложения) больше не добавляют или добавляют тихо, медленные
  (поиск по диску) показывают загрузку в своей группе и не держат
  индикатор всего поиска.
- Лимит времени на провайдер: 30 с вместо 5 с, одна глобальная
  переменная, плагин может её поменять: `scope.providerTimeLimitMs`
  (общая на всех, движок читает её на каждый запрос).
- Props и Style пока остаются `data class` (удобный `copy`). Новое
  поле ломает собранные плагины — их отсечёт версия API в манифесте,
  пересобрать. Перед чужими плагинами или когда API устоится —
  перейти на ABI-стабильные классы (Poko + `copy { }`) и убрать
  параметры по умолчанию из API (см. ресерч, ABI).
- Загрузка в группе — автоматически, без API: группа показывает
  индикатор в заголовке, пока поток её провайдера не завершился
  (`ResultGroup.loading`). Минус принят: незавершающийся поток держит
  индикатор до лимита времени.
- Порядок плагинов, трогающих один компонент, — пока любой.
- Внешние плагины ставятся APK, встроенные — в APK хоста. Изоляцию
  ошибок пока не делаем.
- Калькулятор: нампад рисуем сами, детали — при создании плагина.
- Подсказку команд делаем, продумать позже.

## Layout Pixel Search (по скриншоту)
1. Сверху строка: лого слева, поле, кнопка фильтров справа.
2. Середина пустая, видны обои: окно поверх обоев с затемнением.
3. Результаты прижаты к низу, к клавиатуре (`reverseLayout`).
4. Ряд из 5 приложений с подписями. Первое подсвечено — цель Enter.
5. Ряд «искать в…»: круглая кнопка веб-поиска + иконки

## DexClassLoader
- Формат плагина: обычный APK из модуля `com.android.application`.
  Точка входа и версия API — в `<meta-data>` манифеста.
- Читать через `getPackageArchiveInfo(path,
  GET_META_DATA or GET_SIGNING_CERTIFICATES)`: versionCode,
  точка входа и подпись одним вызовом.
- Android 14+: файл с dex должен быть read-only
  (`file.setReadOnly()`), иначе SecurityException.
- Копировать в internal storage:
  `filesDir/plugins/<id>/<versionCode>.apk`, для каждой версии новый
  файл. Из внешнего хранилища не грузить.
- `DexClassLoader(path, null, null, hostClassLoader)`, parent-first:
  Compose, Kotlin, coroutines и API плагин получает от хоста.
- В плагине API, Compose, stdlib, coroutines, OkHttp и
  kotlinx.serialization — `compileOnly`.
  Свои зависимости плагин вшивает в себя; у каждого плагина свой
  загрузчик, поэтому конфликтов нет, пока эти типы не ходят через API.
- **R8 в хосте** вырезает неиспользуемые функции Compose, и плагин
  падает с `NoSuchMethodError`. Варианты: не минифицировать хост или
  добавить `-keep` для `androidx.compose.**`, `kotlin.**`,
  `kotlinx.coroutines.**`, `kotlinx.serialization.**`, `okhttp3.**`
  и API.
- Версии Kotlin/Compose у плагина и хоста одни (общий version
  catalog). При загрузке проверять версию API из manifest.
- ABI: в публичном API без `data class` и параметров по умолчанию —
  новое поле ломает собранные плагины. Проверка:
  `binary-compatibility-validator`.
- Выгрузка: убрать из реестра всё, что зарегистрировал плагин,
  `onUnload`, сменить `key(generation)` вокруг корня UI. Классы
  уйдут вместе с загрузчиком при GC. Горячая замена = выгрузка +
  загрузка с нового пути.
- Ресурсы: проще Compose без Android-ресурсов (`ImageVector`, байты).
  Если понадобятся — `getResourcesForApplication` с подставленными
  `sourceDir` / `publicSourceDir`.
- Нативные библиотеки (`librarySearchPath`) пока не нужны.
- Первый запуск dex медленнее (интерпретатор/JIT). Встроенные плагины
  компилировать в APK, внешние грузить в фоне.

## Изоляция ошибок
- В Compose нет error boundaries, исключение в composition роняет
  процесс.
- Маркер «гружу X» перед `install`, снять после. Остался при старте →
  отключить X.
- Пакет плагина = его id. В `UncaughtExceptionHandler` по кадрам
  стека найти плагин, отключить, перезапуститься (safe mode).
- Логика: каждый middleware в try/catch, при ошибке вызвать `next`
  с тем же входом и пометить плагин.

## Доставка плагинов
- `adb push` в `/sdcard/Android/data/<pkg>/files/inbox/` под
  временным именем, затем `mv`. Хост ловит `FileObserver` + проверка
  на resume.
- Termux не может писать в `Android/data` (scoped storage). Для
  сборки внутри приложения проще встроенный proot: APK сразу в своём
  `filesDir`.
- Безопасность: плагин работает со всеми правами хоста. Принимать
  только разрешённые сертификаты (свой ключ), для чужих —
  подтверждение при первой установке.

## Ограничения манифеста
- Плагин не может добавить разрешения, роли, Activity, Service,
  виджеты. Хост объявляет заранее с запасом: `QUERY_ALL_PACKAGES`,
  контакты, интернет, роль ASSIST.
- Плагинам: API запроса разрешений, экраны-маршруты вместо Activity,
  общий фоновый worker.

## Поиск (логика)
- Каждый провайдер в своей корутине, `flatMapLatest` на запрос,
  таймаут на провайдер, результаты потоком.
- Видимые элементы не переставлять, новые добавлять ниже.
- Ранжирование: score провайдера + frecency по истории запусков.
- Возможные точки расширения: `query.transform`, `providers`, `rank`,
  `group`, `item.actions`, `action.handle`, `key.enter`, `lifecycle`.
- `Item`: id, тип, title, score + расширяемые `extras`.

## Compose-механика компонентов
- `@Composable operator fun invoke` у класса работает:
  `SearchBar(props)` выглядит как обычный вызов.
- Цепочка переопределений: `fold` по списку, обёрнутый в
  `remember(overrides)`.
- Изменение стиля — `@Composable (Style) -> Style`, внутри можно
  читать `MaterialTheme`.
- Локальная подмена в поддереве — `CompositionLocalProvider` с другой
  картой переопределений.
- Layout-компоненты как в `Scaffold`: получают детей лямбдами и только
  расставляют. Перенос строки вниз = переопределить layout-компонент.
- Тема — обычный `MaterialTheme`. Свои значения плагин держит в своём
  `CompositionLocal`.

## Отброшенные варианты
- Дерево layout + свои токены + UI-кит + JSON-оверлеи в core:
  получается фреймворк поверх Compose, отклонено.
- Интерфейсы компонентов + делегирование `by` для частичной подмены:
  новый метод в интерфейсе ломает собранные плагины
  (AbstractMethodError) или обходит чужие переопределения через
  default-метод. Работу `by` с `@Composable` не проверял.
- Два APK (хост + продукт) — см. `self-modifying-apps.md`.
